## 本轮反思

- 这轮最重要的变化不是技术栈本身，而是产品视角的切换。当前项目不再只是“导入和整理知识”，而是开始建设测试人员真正会使用的知识入口。
- 如果还继续把 retrieval export 单独当主线推进，产品落地会再次被拆散；把它并入问答产品实现，更符合当前目标。
- 第一阶段主动压住范围很关键。只做“缺陷 + 用例问答台 v1”，能让前后端和检索链路在一个可控范围内落地。

## 经验

- 当用户目标已经从“技术底座”切到“产品使用”，计划必须同步改写，不能继续沿用纯技术导向的主线。
- 对话产品的核心不是页面数量，而是回答可信度，因此“引用必带、无证据不肯定回答”必须在计划阶段就写成硬约束。
- 新引入前端和后端时，先把最小读取、检索和详情链路打通，比先追求完整后台和复杂能力更稳。

## 下一步建议

- 下一轮从 retrieval export 和 FastAPI records/chat API 开始。
- 前端先做问答页、引用区和详情抽屉，不再扩更多页面。
- 真正的模型 provider 保持抽象层，先用 fake client 把回归链路做稳。
