# 测试知识问答台 v1 设计说明

## 1. 背景

当前仓库已经完成了基于 Excel 的缺陷与测试用例结构化导入，并形成了可追溯的知识底座。但从测试人员视角看，现阶段仍然缺少一个“可直接使用”的知识入口。

测试人员真正的使用方式不是查看导入日志或质量报告，而是直接提问，例如：

- 这个问题以前是否出现过？
- 某个模块有哪些相关测试用例？
- 这个缺陷需要重点回归什么？
- 某个报错可能关联哪些历史问题？

因此，下一阶段的首要目标不应继续扩 Phase 1 的导入规则，也不应直接跳到完整的自动化平台，而应先建设一个**面向测试人员的对话式知识查询入口**。

## 2. 产品目标

第一期产品目标定义为：

**测试知识问答台 v1**

它面向测试人员，基于当前已经入库的：

- 缺陷（defect）
- 测试用例（testcase）

提供：

- 对话式提问
- 基于知识库的受控回答
- 强制引用来源
- 回到原始记录详情

该产品的核心价值是：让测试人员可以直接“问”和“查”，而不是先理解底层知识结构。

## 3. 第一阶段范围

### 3.1 in scope

第一期只做以下能力：

1. 对话式问答入口
2. 基于现有缺陷和用例的检索
3. 模型生成的简短回答
4. 引用来源展示
5. 原始记录详情查看
6. 最近会话与基础会话保存

### 3.2 out of scope

第一期明确不做：

- PRD 接入
- 技术详设接入
- API 自动化接入
- UI 自动化接入
- 知识编辑后台
- 多知识源混合推理
- 复杂 agent workflow
- 权限系统
- 完整的自动化平台编排

## 4. 目标用户

第一期只站在**测试人员**视角设计，不以研发、产品经理、管理员为主视角。

目标用户的典型需求：

- 快速定位类似历史缺陷
- 根据缺陷找相关测试用例
- 根据模块、现象、错误信息做知识查询
- 在问答结果基础上快速回到原始记录核对

## 5. 核心产品原则

### 5.1 对话式交互优先

第一期主入口是对话框，而不是复杂后台列表页。

### 5.2 回答必须可追溯

系统输出的回答必须附带引用来源，并且来源必须可点击进入原始记录。

### 5.3 没有引用，不输出肯定式结论

如果系统没有找到可靠证据：

- 可以返回“未找到足够证据”
- 可以返回候选记录
- 但不能生成带确定口吻的回答

### 5.4 优先服务查询使用，而不是管理维护

第一期重点是“让测试人员用起来”，而不是“让管理员维护知识库”。

## 6. 页面结构设计

第一期推荐页面结构如下：

### 6.1 左侧：会话侧栏

展示：

- 新建会话
- 最近提问
- 常用问题入口
- 会话切换

作用：

- 保留知识问答的上下文感
- 降低重复提问成本

### 6.2 中间：问答主区

展示：

- 用户问题
- 系统回答
- 推荐回归点 / 结论摘要
- 输入框

要求：

- 页面密度偏紧凑，不要留大块空白
- 更像真实产品，不像设计说明页

### 6.3 右侧：引用来源区

展示：

- 命中的缺陷 / 用例卡片
- 命中片段
- 记录类型
- “查看原始记录”入口

右侧引用区的作用是让测试人员快速判断：

- 系统为什么给出这个回答
- 回答是否可信
- 是否需要进一步看原始记录

## 7. 详情查看交互

### 7.1 默认交互

点击“查看原始记录”后，默认使用**右侧详情抽屉**打开。

原因：

- 不打断当前问答上下文
- 适合快速核对
- 用户不必频繁跳页

### 7.2 深看交互

如果用户需要深度查看，再从抽屉进入独立详情页。

### 7.3 详情信息结构

详情默认展示 4 类信息：

1. 基本信息
   - 编号
   - 标题
   - 类型
   - 状态
   - 模块
   - 严重度 / 优先级

2. 命中片段
   - 为什么会命中
   - 哪一段内容被引用

3. 核心正文
   - 步骤
   - 预期
   - 实际

4. 来源与质量信息
   - source
   - version
   - quality flags

## 8. 技术架构

第一期采用：

- 前端：React
- 后端：FastAPI

### 8.1 React 负责

- 对话页
- 会话侧栏
- 回答展示
- 引用卡片展示
- 详情抽屉 / 详情页

### 8.2 FastAPI 负责

- 问答接口
- 检索接口
- 记录详情接口
- 会话保存接口

### 8.3 知识底座

第一期仍直接消费当前仓库中的知识底座：

- 已入库缺陷
- 已入库用例
- retrieval-ready chunks（下一阶段产物）

## 9. 回答链路设计

第一期回答链路为：

1. 用户提问
2. 后端解析问题
3. 检索命中的缺陷 / 用例
4. 组织引用上下文
5. 生成简短回答
6. 返回答案 + 引用
7. 前端展示问答结果
8. 用户点击查看原始记录

该链路的关键约束是：

- 检索优先
- 回答受控生成
- 引用必须同时返回

## 10. v1 推荐实现策略

第一期推荐策略是：

**先做最小检索 + 受控生成回答**

而不是一开始就追求：

- 多轮 agent 推理
- 多知识源复杂融合
- 自动化平台联动

原因：

- 更容易落地
- 更容易验收
- 更符合当前仓库的真实成熟度

## 11. API 边界（产品层）

第一期后端至少需要提供：

- 问答接口：接收问题，返回回答与引用
- 记录详情接口：按 ID 返回完整缺陷 / 用例记录
- 会话接口：保存最近问题与会话状态

此处只定义产品接口边界，不在本设计阶段展开到字段级 API contract。

## 12. 第一阶段验收标准

第一期可以视为达标，至少需要满足：

1. 测试人员可以通过对话框提出自然语言问题
2. 系统能基于现有缺陷和用例返回回答
3. 每次回答都能附带引用来源
4. 每条引用都能回到原始记录
5. 详情信息足以支持人工核对
6. 对没有足够证据的问题，不输出肯定式结论

## 13. 后续演进方向

在 v1 完成后，后续再逐步扩展：

1. 接入 PRD 与技术详设
2. 扩展到更多知识类型
3. 对接 API 自动化
4. 对接 UI 自动化
5. 扩展成完整测试知识平台

## 14. 结论

当前最合理的下一步不是继续扩 Phase 1 导入规则，也不是直接做完整平台，而是：

**先建设“测试知识问答台 v1”**

它将成为测试人员真正可使用的第一入口，也是后续扩展为完整测试知识平台的产品基础。
